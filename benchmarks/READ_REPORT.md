# Повторное сравнение GET с Redis

Историческая серия до оптимизации памяти. Текущая буферизация и повторная проверка скорости описаны в [MEMORY_REPORT.md](MEMORY_REPORT.md).

Дата UTC: 2026-11-06T08:17:41Z. Платформа: `macOS-27.0.1-arm64-arm-64bit-Mach-O`.
Версия Redis: `Redis server v=8.10.2 sha=00000000:1 malloc=libc bits=64 build=764b3e45065a66fb`.

Сравниваются предыдущая версия (из ответа с 1,11 млн GET/с), текущая release-сборка и Redis. Семь прогонов по 1 000 000 запросов для каждого сервера и размера значения. Порядок серверов чередуется; образцы и SHA256 бинарников — в [read-results.json](read-results.json).

Одинаковый сценарий для всех: 50 постоянных TCP-подключений, loopback, pipeline 16, GET существующего горячего ключа. В таблице медиана операций/с.

| Размер значения | Предыдущая версия | Текущая версия | Redis |
|---|---:|---:|---:|
| 64 байт | 1 212 121 | 2 232 143 | 1 915 709 |
| 4096 байт | 250 627 | 425 351 | 632 511 |

Для 64 байт медиана ExpenseKV выше Redis на 16.5%. В шести из семи соответствующих прогонов ExpenseKV быстрее Redis; в одном медленнее. Для 4 KiB Redis сохраняет преимущество по медиане. Результаты заметно колеблются: это вывод об измеренной пропускной способности конкретного сценария, а не общее превосходство над Redis.

## Задержка

Медианы показателей, которые выдаёт redis-benchmark, в миллисекундах:

| Значение | Средняя ExpenseKV | Средняя Redis | p99 ExpenseKV | p99 Redis |
|---|---:|---:|---:|---:|
| 64 байт | 0.194 | 0.348 | 0.695 | 0.551 |
| 4096 байт | 0.644 | 0.554 | 3.543 | 2.927 |

Улучшение медианы throughput для 64 байт не означает выигрыш по p99: в этой серии p99 ExpenseKV выше Redis.

## Изменения

- Полные кадры уже полученных GET разбираются без копирования аргументов. Неполные кадры и другие команды проходят обычный потоковый парсер с теми же ограничениями.
- До 64 последовательных GET обрабатываются под одной блокировкой чтения RwLock. Разные клиенты читают параллельно; изменения и обслуживание сохраняют исключительную блокировку. GET не перескакивает через SET, AUTH, DEL и другие команды.
- Сериализация пачки идёт в один собственный буфер без отдельного выделения памяти и клонирования ссылки для каждого ответа. Блокировка освобождается до сетевой отправки. Значения хранятся в неизменяемых Arc; одиночные ответы могут разделять данные без копирования.
- Пачка ограничена 2 MiB значений плюс RESP-заголовки. Оставшиеся кадры обрабатываются следующей пачкой. Сетевой буфер записи — 64 KiB на соединение.
- TTL проверяется при чтении; физическое удаление выполняет обслуживание или путь записи. Hit/miss обновляются атомарно один раз на пачку.
- Формат WAL и sync_data перед подтверждением изменений сохранены. Групповой fsync не добавлялся.

## Проверки

21 тест проходит; Clippy без предупреждений, release-сборка с --locked успешна. Среди проверок: каждый разрез бинарного RESP-кадра, ограничения парсера, большие пачки с ограничением 2 MiB, порядок GET/SET/DEL, частичный запрос, повторный неуспешный AUTH, 8 параллельных читателей с записями и точным учётом hit/miss. Существующие проверки восстановления WAL, повреждений, компактации и атомарности также проходят.

## Условия и пределы вывода

У Redis сохранены параметры прежнего сравнения: appendonly yes, appendfsync always, io-threads 1; RDB и автоматическая перезапись AOF выключены. У ExpenseKV компактация отодвинута порогом 1 GiB. Оба используют отдельные временные каталоги и лимит оценки данных 64 MiB. В тесте GET записи происходят только при подготовке ключа.

ExpenseKV использует несколько потоков для параллельных чтений; CPU-бюджет между серверами не нормировался. Загрузка CPU и RSS не измерялись. Redis с другим числом IO-потоков, холодные и случайные ключи, большие базы, Linux, длительная смешанная нагрузка и Django в эту серию не входят. Параллельная запись и более крупные значения остаются отдельными задачами. Полная функциональная совместимость с Redis не заявляется.

## Повторение

```sh
cargo build --release --locked
python3 benchmarks/compare.py --operations GET --cases pipeline --runs 7 --read-requests 1000000 --output benchmarks/read-results.json
```

Для включения прежнего бинарника добавьте --baseline-binary /path/to/previous/expense-kv. Без этого параметра сравниваются текущая версия и Redis. Исторические бинарники в репозиторий не включены; идентификатор каждой измеренной сборки — SHA256 в JSON. Для повторения исторического сравнения нужен соответствующий прежний бинарник.

Первый этап, включая измерения записи до этой оптимизации: [REPORT.md](REPORT.md).
