## Что следует из замеров

- GET 64 байта, 50 клиентов и pipeline 16: 192 тыс. → 1111 тыс. операций/с, рост в 5.80 раза. p99: 6.623 → 1.279 мс. Redis: 1.85 млн операций/с.
- GET 64 байта без pipeline у одного клиента: 38.7 тыс. → 50.5 тыс. операций/с. Медиана Redis: 46.7 тыс. Разброс образцов не позволяет переносить это преимущество на другие нагрузки.
- У параллельной записи Redis сохраняет большое преимущество. ExpenseKV синхронизирует каждую изменяющую команду отдельно; группового fsync нет.
- Запись не стала стабильно быстрее во всех сценариях. Для SET 64 байта, 50 клиентов, без pipeline: 346 → 248 операций/с. С pipeline 16 p99 вырос с 209 до 407 мс. Короткие прогоны с fsync чувствительны к состоянию диска и планированию потоков. Эти результаты не дают оснований обещать ускорение или снижение хвоста задержки записи.

## Условия и ограничения

Два горячих ключа, TCP loopback, постоянные соединения, значения 64 байта и 4 KiB. GET читает существующее значение; SET перезаписывает другой ключ. На сценарий и прогон приходится 50 000 GET и 600 SET (800 SET при 50 клиентах и pipeline 16). Порядок серверов чередуется. Запросы к разным серверам не выполняются одновременно.

RDB и автоматическая перезапись AOF Redis отключены. У ExpenseKV порог компактации поднят до 1 GiB. Все серверы используют изолированные временные каталоги; существующие пользовательские базы для теста не используются. Лимит оценки памяти — 64 MiB; значения этой оценки у серверов имеют разную методику расчёта.

Короткие прогоны и небольшое число SET чувствительны к фоновым задачам и состоянию накопителя; p99 записи ориентировочный. Это не испытание больших наборов ключей, массового истечения TTL, длительной нагрузки, Django или сбоя питания. Результат не доказывает общего превосходства над Redis.

## Проверка корректности

- `cargo test`: 15 тестов прошли, включая partial frames, pipeline, AUTH, бинарные ответы, TTL, лимит памяти, ошибки WAL, компактацию и каждый возможный обрыв последней пакетной записи.
- `cargo clippy --all-targets -- -D warnings`: без предупреждений; release-сборка с `--locked` успешна.
- Дополнительная проверка отдельных процессов: WAL исходной версии открыт новой, выполнены 200 INCR из 8 параллельных клиентов без потери обновлений, SAVE и последующая запись. После SIGKILL новый WAL успешно открыт исходным бинарником; счётчик, бинарное значение и TTL сохранены. SIGKILL проверяет аварийное завершение процесса, не сбой питания.

## Повторение

```sh
cargo build --release --locked
python3 benchmarks/compare.py --baseline-binary /path/to/previous/expense-kv
```

Без `--baseline-binary` сравниваются только новая версия и Redis. Для длинного прогона добавьте `--read-requests 1000000 --write-requests 10000`.

Методика: [redis-benchmark](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/benchmarks/), [Redis persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/).
