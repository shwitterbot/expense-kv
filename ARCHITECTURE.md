# Устройство ExpenseKV

## Файлы

| Файл | Ответственность |
|---|---|
| `src/main.rs` | Конфигурация, TCP, лимит клиентов, AUTH, фоновое обслуживание |
| `src/protocol.rs` | Ограниченный по размеру парсер RESP2, кодирование ответов |
| `src/store.rs` | HashMap, TTL, команды, атомарность, лимит записей |
| `src/journal.rs` | WAL, контрольные суммы, replay, сжатие, файловая блокировка |

Следующие файлы относятся к внешнему проекту ExpenseTrackerDjango и в этот репозиторий не входят:

| Файл внешнего проекта | Ответственность |
|---|---|
| `ExpenseTracker/expense_kv/client.py` | Python-клиент RESP2 без сторонних зависимостей |
| `ExpenseTracker/expenses/cache.py` | Чтение/заполнение JSON-кэша и fallback |
| `ExpenseTracker/expenses/signals.py` | Обновление поколений данных в SQL |
| `ExpenseTracker/expenses/reports.py` | Месячная сводка и валидация периода |

## Обработка команды

TCP-поток может прийти частями. Парсер читает длины до выделения буфера, затем ровно столько байт и проверяет CRLF. Обычный перевод строки внутри значения допустим: протокол бинарный. Неограниченные заголовки, отрицательные длины аргументов, вложенные массивы и oversized-запросы отклоняются. После протокольной ошибки соединение закрывается, остальные клиенты продолжают работать.

У каждого соединения свой поток, BufReader ёмкостью 8 KiB и BufWriter ёмкостью 64 KiB. `RwLock<Store>` позволяет выполнять GET параллельно; изменения, остальные команды и обслуживание используют исключительную блокировку. Условия NX/XX, старое значение счётчика, WAL и новое значение обрабатываются под одной блокировкой записи, поэтому обновления не теряются. Сетевые чтения и записи выполняются после освобождения блокировки.

До 64 последовательных GET из уже полученных полных кадров выполняются под одной блокировкой чтения. Разбор кадров использует заимствованные срезы аргументов. Целевой размер сериализованной пачки — 256 KiB с запасом под RESP-заголовки; оставшиеся кадры обрабатываются следующей пачкой. Одно допустимое значение до 1 MiB может превысить этот целевой размер и тогда обрабатывается отдельно. Чтение не перескакивает через SET, AUTH или другую команду. GET проверяет абсолютный TTL, не изменяя таблицу; физическое удаление выполняет обслуживание или путь записи. Счётчики hit/miss атомарны и обновляются один раз на пачку. Значения и одиночные bulk-ответы используют `Arc<[u8]>`. Pipeline сериализуется сразу в один собственный буфер под блокировкой чтения, без выделения памяти и клонирования ссылки для каждого ответа. Буфер принадлежит соединению и используется повторно; увеличенный буфер после значения больше 256 KiB освобождается при следующей меньшей пачке. Затем блокировка освобождается и буфер отправляется в сеть. Ответ сохраняет своё значение, даже если другой клиент уже перезаписал ключ. Сетевые буферы и старые значения, удерживаемые одиночными ответами, не входят в оценку памяти живой таблицы.

Ответы объединяются в ограниченном буфере. Перед чтением из сокета, способным блокироваться, буфер отправляется; это работает и при частично полученном следующем запросе. После команды буфер также отправляется, если с предыдущего flush прошла хотя бы 1 мс. Подтверждения изменения WAL отправляются сразу. QUIT и протокольная ошибка отправляют накопленные ответы. MSET записывает все пары одним действием; дубликаты ключей используют последнее значение. MULTI/EXEC не реализованы.

`GET` выполняет ожидаемый O(1) поиск в HashMap. Очистка, DBSIZE и INFO удаляют только просроченные записи через BTreeSet без полного обхода таблицы. Изменение TTL обновляет ровно одну запись индекса на ключ. Компактация обходит все живые записи и требует O(n). Запись включает fsync и не является операцией с постоянной задержкой в реальном времени.

## Сохранение

После изменения размера WAL `Store::execute` вместе с ответом возвращает признак немедленной отправки. Сетевой слой сразу сбрасывает буфер после подтверждённой записи, не задерживая её ответ ради объединения следующих команд. Условный SET без изменения данных и DEL отсутствующего ключа не требуют такой отправки.

На диске лежат `LOCK`, `data.aof` и временный `rewrite.tmp` во время компактации. Новые файлы журнала создаются с правами 0600, новые каталоги — 0700. Второй процесс с тем же каталогом получает ошибку OS file lock; после аварийного завершения блокировка снимается системой. Файл LOCK удалять для снятия блокировки нельзя.

Формат `data.aof` начинается с восьми байт `EKVAOF01`. Каждая следующая запись содержит:

1. длину payload: u32 little-endian;
2. CRC32 четырёх байт длины;
3. CRC32 payload;
4. payload: число изменений u32, затем операции SET, DELETE или CLEAR.

SET хранит длины ключа/значения, абсолютное время окончания TTL i64 в миллисекундах Unix (`-1` — без TTL), затем исходные байты. MSET/DEL с несколькими ключами составляют одну журнальную запись. CRC защищает от случайной порчи; это не криптографическая подпись.

CRC32 вычисляется табличным алгоритмом с тем же полиномом и результатом, что в исходной версии. Заголовок и payload формируются в одном буфере и передаются одним `write_all`. Чтение при replay и запись при компактации буферизованы; формат файла сохранён.

Порядок успешного изменения:

1. Проверить аргументы, условия и квоту памяти.
2. Добавить полную запись в WAL.
3. Выполнить `sync_data`.
4. Изменить HashMap.
5. Вернуть подтверждение клиенту.

Если файловая операция завершилась ошибкой, значение в памяти не меняется, сервер отвечает MISCONF и запрещает следующие изменения до перезапуска после устранения причины. Операция, ответ на которую не пришёл, может восстановиться при replay, если её запись всё же полностью попала на диск. Поэтому клиент не повторяет записи автоматически. Гарантии fsync зависят также от ОС, файловой системы и накопителя.

При запуске сервер последовательно проверяет и применяет WAL. Только незавершённая последняя запись обрезается до последней корректной границы; повреждение полной записи или её длины останавливает запуск. Сервер не скрывает порчу пропуском данных. Максимальный размер журнальной записи ограничен. Восстановление большого журнала последовательно и блокирует начало приёма клиентов.

## TTL и компактация

Истечение TTL проверяется при доступе к ключу и фоновым удалением просроченных записей из индекса раз в секунду. Индекс восстанавливается из живых записей при запуске; его оценочная стоимость включена в лимит памяти. TTL хранится как абсолютная дата, поэтому не начинается заново после перезапуска. Нужны корректные системные часы: их существенный перевод влияет на срок жизни. Массовое одновременное истечение может задержать остальные команды, поскольку очистка использует исключительную блокировку.

Обычный SET без EX/PX снимает предыдущий TTL. INCR/DECR/INCRBY сохраняют TTL. EXPIRE/PEXPIRE со значением <= 0 удаляют существующий ключ. PTTL возвращает миллисекунды, TTL — целое число секунд с округлением вниз; `-1` означает отсутствие TTL, `-2` — отсутствие ключа. Отдельные граничные детали TTL могут отличаться от Redis.

Автоматическая компактация выполняется, когда журнал больше `max(KV_COMPACT_BYTES, 2 * used_memory_estimate)`. Под исключительной блокировкой создаётся полный файл живых записей `rewrite.tmp`, выполняются fsync, атомарная замена `data.aof` через rename и fsync каталога. После rename активный дескриптор сразу переключается на новый файл. Старый LOCK остаётся заблокированным на отдельном inode. Незавершённый временный файл при следующем старте игнорируется; источником восстановления служит data.aof. `SAVE` делает ту же процедуру по запросу.

## Корректность кэша Django

Одного `DEL user:report` после изменения расхода недостаточно: Rust-сервер в этот момент может не работать, а параллельный читатель может записать устаревший результат уже после DEL.

Здесь модель `CacheGeneration` хранит UUID для `user:<id>` и общего пространства `categories`. Сохранение Transaction/Category и обновление UUID идут в одной SQL-транзакции. Django deletion collector также выполняет удаление с сигналами в транзакции. При смене владельца обновляются обе пользовательские версии. Изменение категории меняет общую версию, в том числе при SET_NULL ссылок после удаления.

При чтении Django:

1. Получает текущие UUID из SQL.
2. Строит ключ из namespace, user_id, UUID и хеша типа/параметров ответа.
3. Возвращает подходящий JSON из ExpenseKV, если он есть.
4. Иначе вычисляет результат и записывает его с TTL по тому же ключу.

Когда запись SQL меняет UUID, прежние ключи становятся недоступны для следующих читателей и позднее истекают сами. Позднее завершившийся читатель может записать старый результат, но только под старым ключом. При перекрывающихся чтении и записи текущий читатель может увидеть старую версию, как и при обычном чтении БД; запросы, начавшиеся после успешной записи, используют новое поколение.

При cache hit остаются две короткие SQL-проверки версий; мы экономим чтение и сериализацию списка, а не все обращения к основной БД. Во внешнем `transaction.atomic()` кэш обходится, чтобы не публиковать данные до commit. При включённом ATOMIC_REQUESTS это означает BYPASS для всего такого запроса.

Ошибка сети, таймаут, OOM, ошибка AUTH или некорректный JSON приводят к чтению основной БД. Запись транзакций вообще не требует доступности KV. Таймаут сокета — предел отдельной операции, не строгий deadline всего HTTP-запроса. Circuit breaker и пул соединений не реализованы; клиент открывает одно соединение на команду и безопасен для нескольких Django worker-процессов.

Кэш рассчитан на текущую единственную основную БД проекта. Для конфигурации с database routers нужно передавать один alias во все чтения поколений, данных и проверку atomic-блока.

## Массовые изменения данных

`QuerySet.update()`, `bulk_create()`, `bulk_update()`, raw SQL и загрузка fixtures не вызывают обычный цикл save-сигналов. При добавлении собственного импорта его нужно включить в тот же механизм:

```python
from django.db import transaction
from expenses.models import Transaction
from expenses.signals import bump_generation

with transaction.atomic():
    Transaction.objects.filter(user_id=user_id).update(title="Импортированная операция")
    bump_generation(f"user:{user_id}")
```

Для массового изменения/удаления категорий обновляется `bump_generation("categories")`. При переносе операций между пользователями нужно обновить поколения обоих. После внешнего изменения SQL, восстановления backup или loaddata можно сменить `EXPENSE_KV_NAMESPACE`, вместо обхода всех поколений. Пользовательские UUID не используются для авторизации: её по-прежнему обеспечивают IsAuthenticated и фильтр queryset по request.user.

После этой версии разумны измерения hit rate и времени ответов на реальных данных, ограничение числа сохранённых отчётов, пул клиентских соединений, асинхронный сетевой слой и режимы группового fsync. Эти пункты требуют отдельного проектирования гарантий; они не заявлены как уже реализованные. Локальный воспроизводимый тест Rust-сервера и Redis находится в `benchmarks/compare.py`; он не измеряет интеграцию Django.

Источники формата и API: [RESP](https://redis.io/docs/latest/develop/reference/protocol-spec/), [Django signals](https://docs.djangoproject.com/en/6.0/topics/signals/), [Django transactions](https://docs.djangoproject.com/en/6.0/topics/db/transactions/). Это ссылки на спецификации, а не заявление о полной совместимости с Redis.

## Измерение памяти

`benchmarks/memory.py` сравнивает RSS двух отдельных процессов с одинаковыми уникальными ключами/значениями и настройками сохранения. На macOS дополнительно собираются physical footprint и системный lifetime peak через proc_pid_rusage. Пустой сервер, загруженная база, idle-клиенты, активный GET и FLUSHDB измеряются отдельно. Внутренние used_memory_estimate и used_memory записываются как разные метрики. Состояние сжатия и swap ОС сохранено в JSON. Подробности — в `benchmarks/MEMORY_REPORT.md`.
