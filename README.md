# ExpenseKV

Небольшой персистентный сервер ключ–значение на Rust без внешних Rust-зависимостей.
Принимает ограниченное подмножество RESP2; предназначен для строк и JSON-кэша ExpenseTracker.

В этом репозитории находятся самостоятельный сервер, тесты и воспроизводимые эксперименты.
Код Django-приложения в него не входит.

## Измеренные результаты

Локальное сравнение на macOS ARM64: 50 клиентов, pipeline 16, Redis 8.10.2 с
`io-threads=1` и AOF `appendfsync always`. Скорость — медиана семи прогонов по миллиону
GET существующего горячего ключа; память — отдельная серия из трёх прогонов.

| Сценарий | ExpenseKV | Redis |
|---|---:|---:|
| GET, значение 64 байта | 2,50 млн/с | 1,89 млн/с |
| GET, значение 4 KiB | 859 тыс./с | 892 тыс./с |
| Пик footprint при GET, база 512 × 64 KiB | 59,36 MiB | 48,16 MiB |

Это результат конкретной конфигурации и нагрузки. CPU-бюджет не нормировался;
общего превосходства по скорости, задержке или памяти не заявляется.
[Методика, ограничения и исходные измерения](benchmarks/MEMORY_REPORT.md).

## Запуск

Нужны Rust 1.89+ и Linux/macOS.

```sh
cargo test
cargo build --release --locked
KV_DATA_DIR=./data KV_BIND=127.0.0.1:6380 ./target/release/expense-kv
```

В другом терминале:

```sh
redis-cli -p 6380 SET report '{"total":12500}' EX 60
redis-cli -p 6380 GET report
redis-cli -p 6380 INFO
```

Для доступа по внешнему адресу задайте `KV_PASSWORD`. Пароль передаётся командой AUTH;
TLS сервер не поддерживает, для недоверенной сети нужен защищённый транспорт.

## Конфигурация

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `KV_BIND` | `127.0.0.1:6380` | TCP-адрес |
| `KV_DATA_DIR` | `./data` | Каталог журнала и блокировки |
| `KV_PASSWORD` | пусто | Пароль AUTH; обязателен для внешнего адреса |
| `KV_MAX_BYTES` | `67108864` | Лимит оценки памяти записей |
| `KV_MAX_CLIENTS` | `128` | Одновременные подключения, максимум 4096 |
| `KV_TIMEOUT_SECONDS` | `10` | Таймаут отдельного чтения/записи сокета |
| `KV_COMPACT_BYTES` | `16777216` | Нижний порог автоматической компактации |

`KV_MAX_BYTES` ограничивает оценку размера данных, а не RSS процесса. Оценка включает
байты ключей/значений, 64 байта на запись и для ключа с TTL ещё длину ключа + 48 байт
на индекс. Потоки, сетевые буферы, ёмкость HashMap и временные выделения памяти имеют
дополнительную стоимость. Автоматического вытеснения ключей нет: сервер возвращает OOM.

## Команды

- `PING [message]`, `ECHO message`, `AUTH password`, `QUIT`.
- `GET key`, `MGET key ...`, `SET key value [NX|XX] [EX seconds|PX milliseconds]`,
  `MSET key value ...`, `DEL key ...`, `EXISTS key ...`.
- `INCR key`, `DECR key`, `INCRBY key delta` — знаковые целые i64 с проверкой переполнения.
- `EXPIRE key seconds`, `PEXPIRE key milliseconds`, `TTL key`, `PTTL key`, `PERSIST key`.
- `TYPE key`, `DBSIZE`, `INFO`, `SAVE`, `FLUSHDB`, `SELECT 0`.
- `COMMAND` возвращает пустой массив; `CLIENT SETINFO field value` принимается для handshake клиентов.

Поддерживаются бинарные ключи/значения, pipeline, атомарные NX/XX, счётчики и MSET.
Есть только DB 0 и строки. Максимум 1024 аргумента, ключ 1024 байта, аргумент 1 MiB,
сумма байтов аргументов 2 MiB. Сумма байтов значений ответа MGET также ограничена 2 MiB.
Inline-команды, RESP3, MULTI/EXEC, Lua, коллекции, репликация и кластер не реализованы.
Полная совместимость с Redis не заявляется.

## Подключение к Django и другим фреймворкам

Сервер работает отдельно; приложение подключается Redis-клиентом в режиме RESP2.
По умолчанию адрес — `redis://127.0.0.1:6380/0`.

| Фреймворк | Пример |
|---|---|
| Django | [Cache backend](examples/django_backend.py) и [настройки CACHES](examples/django_settings.py) |
| FastAPI | [Async-клиент с lifespan](examples/fastapi_app.py) |
| Flask | [JSON-кэш с пулом соединений](examples/flask_app.py) |
| Express / Node.js | [Клиент ioredis и HTTP-маршрут](examples/express.mjs) |

Для Django установите `redis==8.1.0`, скопируйте backend в пакет своего проекта
и добавьте alias `expensekv` из файла настроек, указав путь к скопированному классу.
Backend использует штатную сериализацию Django; `set_many()` выполняется отдельными
SET без транзакций. После настройки:

```python
from django.core.cache import caches

cache = caches["expensekv"]
cache.set("report:demo", {"total_minor": 12500}, timeout=60)
assert cache.get("report:demo")["total_minor"] == 12500
cache.delete("report:demo")
```

Примеры читают `EXPENSE_KV_URL` и необязательный `EXPENSE_KV_PASSWORD`.
Используется DB 0 и пароль без ACL-имени пользователя. Обычный `RedisCache.set_many()`
и транзакционные pipeline требуют неподдерживаемых MULTI/EXEC, поэтому важны настройки
из примеров. Готовые Redis-адаптеры для очередей/сессий/блокировок отдельно не проверялись.

## Надёжность и производительность

Успешная запись проходит WAL → `sync_data` → изменение памяти → ответ. Ошибка диска
блокирует дальнейшие изменения до перезапуска; при этом уже сохранённые значения доступны
для чтения. Абсолютный TTL переживает перезапуск. Оборванная последняя запись журнала
обрезается при восстановлении; повреждённая полная запись останавливает запуск.

Ответы буферизуются и объединяются при pipeline. Перед ожиданием сетевых данных буфер
всегда отправляется, в том числе если следующий запрос получен частично. Размер буфера
ответов — 64 KiB на соединение; большие ответы отправляются по мере заполнения. После команды буфер также
отправляется, если с предыдущего flush прошла хотя бы 1 мс. Подтверждение изменения WAL
отправляется сразу: следующие fsync в pipeline не удерживают готовый ответ.

TTL хранится в упорядоченном индексе с одной записью на ключ. Фоновая очистка больше
не сканирует ключи без TTL или с будущим TTL. Изменение TTL стоит O(log E), удаление
K просроченных ключей — O(K log E), где E — число ключей с TTL. Массовое одновременное
истечение всё ещё может задержать другие команды.

WAL записывает заголовок и тело одним `write_all`; CRC32 вычисляется через таблицу.
Восстановление и компактация используют буферизацию. Формат `EKVAOF01` сохранён,
миграция журнала не нужна. Новая оценка памяти учитывает индекс TTL: при данных близко
к лимиту для открытия существующего каталога может понадобиться увеличить `KV_MAX_BYTES`.

Последовательные GET из уже полученного буфера обрабатываются пачкой до 64 команд
под общей блокировкой чтения `RwLock`. Целевой размер сериализованной пачки — 256 KiB;
остальные команды остаются во входном буфере для следующей пачки. Одно значение больше
этого размера обрабатывается отдельно, до предела протокола 1 MiB. Разбор полных
кадров не копирует аргументы. Значения хранятся в неизменяемых `Arc<[u8]>`. Pipeline
сериализуется сразу в один буфер под блокировкой чтения, затем передаётся в сеть после
освобождения блокировки. Это убирает отдельные выделения памяти и клонирование ссылок
для каждого ответа в пачке. Буфер принадлежит соединению и используется повторно.
После одиночного большого значения увеличенный буфер освобождается при следующей
меньшей пачке. Одиночные ответы могут удерживать старые значения после их перезаписи до отправки,
поэтому лимит данных не является строгим пределом RSS.

Чтения GET выполняются параллельно. Записи, остальные команды и обслуживание берут
исключительную блокировку. GET сразу скрывает истёкшее значение; физическое удаление
выполняется фоновым обслуживанием, проверками при изменениях или при достижении KV_MAX_BYTES.
Каждая изменяющая команда по-прежнему выполняет
собственный `sync_data`; группового fsync нет. Компактация блокирует команды на время
перезаписи. Это существенные ограничения для параллельной записи и больших наборов данных.

## Потребление памяти

```sh
cargo build --release --locked
python3 benchmarks/memory.py
```

Сравнение одинаковых данных с Redis: пустой процесс, заполненная база, TTL,
50 idle-подключений, 50 активных клиентов с pipeline 16 и состояние после FLUSHDB.
Три прогона на каждый сценарий; серверы используют отдельные временные каталоги.
Измеряются RSS ОС и на macOS physical footprint. При сжатии/вытеснении страниц RSS
может сильно меняться и быть меньше объёма данных, поэтому внутренний учёт записей,
RSS и footprint показаны отдельно. `KV_MAX_BYTES` не ограничивает RSS процесса.

## Сравнение с Redis

Актуальное сравнение скорости и памяти — в
[benchmarks/MEMORY_REPORT.md](benchmarks/MEMORY_REPORT.md). Для повторения GET:

```sh
python3 benchmarks/compare.py --operations GET --cases pipeline --runs 7 --read-requests 1000000 --output /tmp/expense-kv-comparison.json
```

Предыдущая серия до оптимизации памяти — в
[benchmarks/READ_REPORT.md](benchmarks/READ_REPORT.md).

Итоги первого этапа с исходной сборкой, предыдущей версией и Redis — в
[benchmarks/REPORT.md](benchmarks/REPORT.md); все 108 образцов — в
[benchmarks/results.json](benchmarks/results.json).

Воспроизводимый локальный тест использует `redis-server` и `redis-benchmark` из PATH:

```sh
cargo build --release --locked
python3 benchmarks/compare.py
```

Чтобы сравнить ещё и предыдущую сборку:

```sh
python3 benchmarks/compare.py --baseline-binary /path/to/previous/expense-kv
```

Тест создаёт отдельные временные каталоги и серверы на свободных loopback-портах,
завершает только свои процессы и сохраняет образцы и медианы в `benchmarks/results.json`.
В каждом сценарии три прогона с чередованием порядка серверов: 64/4096 байт,
1/50 клиентов, pipeline 1/16. GET читает существующий ключ; SET перезаписывает другой.
Это тест двух горячих ключей, а не произвольной рабочей нагрузки. Для записи Redis
включены `appendonly yes`, `appendfsync always`, отключены RDB и автоматическая перезапись
AOF; у ExpenseKV автоматическая компактация отодвинута большим порогом. Для обоих задан
лимит 64 MiB, но определения оценки памяти различаются.

Число SET невелико из-за стоимости синхронизации диска; p99 записи при таком числе
образцов — ориентир. Для более длительного теста используйте `--write-requests 10000`
и `--read-requests 1000000`. Результаты зависят от ОС, диска, нагрузки машины и клиента.
Победу во всех сценариях из такого теста вывести нельзя. Методика и настройка AOF:
[redis-benchmark](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/benchmarks/),
[Redis persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/).

Описание формата WAL и интеграции с внешним Django-проектом — в [ARCHITECTURE.md](ARCHITECTURE.md).
